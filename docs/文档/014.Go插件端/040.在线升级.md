# Go 插件端在线升级与回滚

> 适用版本：提供 Go 插件端的 Jpom 版本。
> 要点：Go 插件端通过「升级容器包」完成在线升级 —— 对 Server 而言它仍是一个合法的 Agent 升级包，对 Go 插件端而言它是携带 Go 可执行文件的容器，解包后**原地替换二进制并重启**。

## 1. 升级包说明

| 包 | 用途 | 说明 |
| --- | --- | --- |
| `agent-go-<version>-upgrade-<os>-<arch>.jar` | **在线升级用**（推荐） | 5 平台容器（linux-amd64、linux-arm64、darwin-amd64、darwin-arm64、windows-amd64）：内含 `go-agent/agent.json` 与对应平台的 `go-agent/bin/go-agent-<os>-<arch>`；对 Server 是合法 Agent 包，Go 插件端识别后自升级 |
| `agent-go-<version>-upgrade.jar` | 兼容别名 | 等同 linux/amd64 容器副本，供旧版 Server **手工上传**、默认回退或不确定节点平台时使用（amd64 Linux 节点） |
| `agent-go-<version>-release-<os>-<arch>.zip` | 全新安装 / 手工替换 | 完整安装包（bin、conf、脚本等）；**不是**在线升级包（Server 的 Go 升级校验要求容器内含 `go-agent/agent.json`） |

:::danger 平台必须完全匹配
升级容器里的可执行文件是**单一平台**的。Go 插件端会校验容器 `agent.json.platform` 与当前进程的 `GOOS/GOARCH` **完全一致**，并校验容器内可执行文件与文件名平台一致；不一致会直接拒绝（提示“升级包平台不匹配”）且**不会改动现有二进制**。因此：
- linux-amd64 节点用 `upgrade-linux-amd64.jar`，linux-arm64 用 `upgrade-linux-arm64.jar`，Windows 用 `upgrade-windows-amd64.jar`，macOS 用对应 darwin 容器；
- 旧版 Server（不支持按平台自动选择）手工上传时也必须上传**节点对应平台**的容器；只有 linux-amd64 节点可以用兼容别名 `upgrade.jar`。
:::

:::warning Java 升级包不能用于 Go 插件端
Java 插件端的 `Agent-<version>.jar` **不能**升级 Go 插件端（Go 插件端没有 JVM 无法执行 jar）。上传该类包时 Go 插件端会返回明确提示：不支持 Java 插件端升级包，请上传包含 `go-agent/agent.json` 与 Go 可执行文件的升级包。
:::

## 2. Server 版本要求

| Server 版本 | 升级方式 |
| --- | --- |
| 已支持识别 Go 插件端（节点 engine=go、按节点平台选择升级包）的版本 | 在「节点管理 → 在线升级」中直接选择/自动获取对应平台的 Go 升级容器（`agent-go-<version>-upgrade-<os>-<arch>.jar`）下发即可；Server 会按节点 `/info` 上报的平台匹配容器 |
| 旧版 Server（低于上述起始版本） | Server 不识别 Go 引擎，请把**与节点平台匹配**的 Go 升级容器**当普通 Agent 升级包手工上传**执行（容器的 MANIFEST 可通过旧 Server 的 jar 校验），或使用离线方式替换二进制 |

:::tip 起始版本
Go 插件端的起始支持版本以对应 Jpom 版本的更新日志/下载页为准（与 Java 插件端同版本号发布）。升级前建议先在测试节点验证。
:::

## 3. 升级前置检查


- [ ] 插件端由 `bin/AgentGo.sh`（Linux/macOS）、`bin\AgentGo.bat`（Windows）或系统服务托管运行中；若用 systemd/nssm，确认退出后会自动拉起（见第 8 节服务管理注意事项）；
- [ ] 下载升级包并校验 sha1；
- [ ] 确认升级包平台与节点一致（`linux-amd64` / `linux-arm64` / `darwin-amd64` / `darwin-arm64` / `windows-amd64`）；
- [ ] 磁盘空间充足（升级会临时占用约 2 倍安装包大小）；
- [ ] 记录当前版本（Server 节点信息，或插件端 `bin/agent -version`）；
- [ ] 如需支持回滚旧版本，确认 `jpom.system.allowed-downgrade` 的配置符合预期（默认不允许降级）。

## 4. 通过 Server 在线升级（推荐）

1. 打开 Server「节点管理 → 在线升级」；
2. 选择/上传**与节点平台匹配**的 Go 升级包：新版 Server 会自动按节点平台选择 `agent-go-<version>-upgrade-<os>-<arch>.jar`；
   旧版 Server 手工上传时，linux-amd64 节点可用兼容别名 `agent-go-<version>-upgrade.jar`，其它平台必须上传对应平台容器；
3. 选择需要升级的一个或多个节点（可只选 Go 插件端节点）；
4. 执行升级，观察进度与结果：
   - Server 会按分片把升级包传到插件端；
   - 插件端校验后替换二进制，并在约 2 秒后重启；
   - Server 在约 10 秒后开始探测节点状态（每秒一次，最多约 2 分钟）；
   - 成功后会刷新显示新版本。
5. 升级完成后在节点监控、项目、脚本页面抽查一遍。

:::tip 升级期间项目会中断吗
升级只重启**插件端进程**，不会主动停止由插件端启动的业务项目进程（前提是项目按标准方式独立启动）。但升级瞬间正在执行的控制台操作（启动/停止/日志推流）会中断，建议避开业务高峰期。
:::

## 5. 升级包校验规则（失败时的返回）

插件端在安装前会做以下校验，任一不通过则**不替换二进制**并返回提示：

| 校验 | 不通过时的提示 |
| --- | --- |
| 包格式/可解压 | 此文件不是 jpom 安装包 |
| 平台匹配 | 升级包平台不匹配：<platform> |
| 最低兼容版本 | 当前程序版本 X 新版程序最低兼容 Y 不能直接升级 |
| 与当前版本相同 | 新包和正在运行的包一致 |
| 版本降级（未允许） | 在线升级不能降级操作 |
| 可执行文件完整性 | 升级包校验失败，可执行文件 sha256 不一致 |
| Java 升级包 | Go 插件端不支持 Java 插件端升级包… |

## 6. 升级过程做了什么（便于排查）

1. 备份当前可执行文件到 `bin/oldJars/`（文件名含版本与时间戳）；
2. 把新可执行文件写入临时文件（`bin/agent.upgrade`）并设置可执行权限，再原子替换 `bin/agent`；
3. 更新 `bin/upgrade.json`（记录 beforeJar/newJar/updateTime/upgradeCount）与 `bin/run.bin`（当前运行的可执行文件名）；
4. 按 `jpom.system.old-jars-count` 清理过旧的备份；
5. 约 2 秒后重启进程（用 `bin/AgentGo.sh` 托管时由脚本/服务管理器拉起）。

## 7. 回滚到上一个版本

### 7.1 手工回滚（推荐，最直接）

```bash
cd /opt/jpom/agent
bin/AgentGo.sh stop
ls -lt bin/oldJars/            # 找到上一个版本备份（文件名含版本与时间）
cp bin/oldJars/<备份文件名> bin/agent
chmod +x bin/agent
bin/AgentGo.sh start
bin/AgentGo.sh status
```

回滚后确认节点在线、版本显示为旧版本即可。

### 7.2 通过升级包降级

若确认允许降级（`jpom.system.allowed-downgrade: true` 并重启插件端），可以把旧版本的 Go 升级包重新上传一次，走第 4 节流程完成降级。

:::danger 默认不允许降级
`allowed-downgrade` 默认为 `false`，此时上传更低版本的升级包会被拒绝（在线升级不能降级操作），请用 6.1 手工回滚。
:::

## 8. 升级失败排查

| 现象 | 排查方向 |
| --- | --- |
| 上传后提示“新包和正在运行的包一致” | 上传的是同版本包；确认版本号与构建时间 |
| 提示“升级包平台不匹配” | 下载了其它平台/架构的容器（如 arm64 节点上传了 linux-amd64 容器）；改用节点对应平台的 `agent-go-<version>-upgrade-<os>-<arch>.jar`；仅 linux-amd64 节点可用兼容别名 `upgrade.jar` |
| 下载中心找不到对应平台 | 在对应版本段落的“Go 插件端在线升级容器”列表中按平台选择；旧版本可能只提供 linux-amd64 兼容别名 |
| 提示 sha256 不一致 | 升级包损坏，重新下载并校验 sha1 |
| 提示不支持 Java 插件端升级包 | 误传了 `Agent-<version>.jar`，改传 Go 升级包 |
| 升级后节点未恢复在线 | 查看插件端 `logs/stdout.log`；确认二进制可执行（`ls -l bin/agent`）、端口与配置未变；必要时按 7.1 回滚 |
| systemd 托管下未自动重启 | service 文件需配置 `Restart=always`（或升级后手工 `systemctl start jpom-agent`） |
| Docker/只读文件系统 | 无法自升级（目录不可写）。**官方未提供 Go 插件端 Docker 镜像**（`jpomdocker/jpom-agent` 是 Java 插件端镜像）；自建镜像时把插件端目录挂载为可写卷才能用在线升级，否则请替换镜像/二进制 |
| systemd/nssm 托管下升级后出现双实例或反复重启 | 只保留一种托管方式（不要同时用服务 + 手工启动）；systemd 配 `Restart=always`、nssm 配 `AppExit Default Restart`；Go 插件端在服务管理器下会把重启交给服务管理器 |

:::warning 服务管理器托管时的升级（重要）
- **Linux systemd**：Go 插件端自升级会在原地重启进程（PID 不变），不会调用 `systemctl`；如希望异常退出后也能自动拉起，service 需配置 `Restart=always`（或至少 `on-failure`）。**不要**依赖 `JPOM_SERVICE` 环境变量——该变量仅 Java 插件端使用，Go 插件端不读取。
- **Windows nssm / sc 服务**：Go 插件端在服务管理器下升级时会把退出交给服务管理器重启，避免出现两个实例。nssm 请设置 `AppExit Default Restart`，并**不要**同时手工 `AgentGo.bat start`；`sc` 注册的服务建议配置失败恢复策略（`sc failure`）。升级前先 `bin\AgentGo.bat status` 确认只有一个实例。
- **macOS launchd**：配置 `KeepAlive` 让升级后自动拉起；手工运行时由 `bin/AgentGo.sh` 负责重启。
:::

## 9. 关于远程升级（检查新版本）

插件端提供「检查远程版本」与「远程升级」能力（与 Java 插件端同一套 Server 接口）。是否可用取决于：

1. Server/版本发布渠道是否提供 Go 插件端升级包；
2. 节点能访问下载地址；
3. 当前版本是否允许升级（同版本/降级/最低兼容版本规则同上）。

若下载中心暂未提供 Go 升级包，请使用第 4 节「上传升级包」的方式。
