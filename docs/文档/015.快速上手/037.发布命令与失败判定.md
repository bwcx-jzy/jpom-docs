## 这个页面解决什么问题

「我在启动脚本里 `exit 1` 了，为什么构建还是成功？」「开了失败即终止，为什么还继续发第二台？」——
这两个问题都出在同一处：**发布命令的退出码算不算「失败」，由「严格执行」决定；失败之后停不停，由「任一目标失败即终止」决定**。两个开关是串联关系，只开一个就会出现「看着没生效」。

::: tip 适用版本
从 **2.11.15.2** 起：发布前/后命令与 SSH 项目重启的退出码每次都会写进构建日志；开启「严格执行」时，非 0 与「读不到退出码（-1）」都会判该目标失败。更早的版本只记录、不判定。
:::

## 一、先分清三个「命令」和一个「重启」

| 位置 | 在哪个步骤 | 失败会怎样 |
| --- | --- | --- |
| 构建命令 | 构建流程 | 无论是否开严格执行，退出码非 0 都可能中断构建（逐行执行时看该行结果） |
| 发布前命令 | 发布操作 | 退出码非 0：不开严格执行只记录；开了判该目标失败 |
| 发布后命令 | 发布操作 | 同上（最常见：启动脚本、健康检查） |
| SSH 项目重启 | 发布操作（发布方式=SSH 项目） | 同上（项目 DSL 里的 restart 脚本） |

判定口径：`0` = 成功；`非 0` = 失败（但要不要判目标失败看「严格执行」）；`-1` = 退出码读不到（严格模式按失败处理，未开只提示）。

## 二、两个开关，各管一段

| 开关 | 位置 | 管什么 | 默认 |
| --- | --- | --- | --- |
| **严格执行** | 编辑构建 → 第 5 步【其他配置】（与「检查仓库差异」「保存构建日志」同一行） | 判断「发布命令/重启退出码非 0」**算不算目标失败** | 关闭 |
| **任一目标失败即终止** | 编辑构建 → 第 4 步【发布操作】 | 判断「一个目标失败后」**要不要停下剩余目标** | 开启 |

组合后的实际行为（多目标发布，例如发布到 2 台 SSH）：

| 严格执行 | 任一目标失败即终止 | 第 1 台脚本 `exit 1` 时的结果 |
| --- | --- | --- |
| 关 | 开 | 只写一行退出码日志，**继续发第 2 台，整体仍判成功** |
| 开 | 开 | 第 1 台判失败 → **跳过第 2 台** → 构建失败 |
| 开 | 关 | 第 1 台判失败 → 继续发第 2 台 → 最终构建失败 |
| 关 | 关 | 只记录，全部继续，最终成功 |

::: warning 常见误解
只勾「任一目标失败即终止」不会让脚本失败停下来——因为它只负责「已经失败的目标之后还要不要继续」，不负责「脚本非 0 算不算失败」。要「脚本失败 → 停 + 判失败」，两个都要开。
:::

## 三、怎么确认已经生效（看构建日志三行）

```text
[SYSTEM-INFO] 开始执行 测试1 发布后命令
[SYSTEM-INFO] 执行 发布后命令 类型脚本的退出码是：7          ← ① 有这行=退出码已读到
[SYSTEM-ERROR] 发布发布后命令退出码 7，「严格执行」已开启，判定该目标失败   ← ② 开严格执行才有
[SYSTEM-INFO] 剩余 1 个目标不再发布                          ← ③ 失败即终止才会出现
构建结束-…            状态：构建失败                           ← ④ 最终状态
```

| 现象 | 说明 |
| --- | --- |
| 没有第 ① 行 | 版本早于 2.11.15.2，或发布命令为空 |
| 有 ① 没有 ② | 「严格执行」没开或没保存（去第 5 步【其他配置】确认） |
| 有 ② 没有 ③ | 「任一目标失败即终止」关了，剩余目标会继续发 |
| 有 ② 但状态仍是成功 | 保存后未重新构建，或被别的任务覆盖了配置 |

## 四、脚本怎么写才不会被误判

### 1. 后台进程要切断输出

```bash
# 推荐：完全脱离终端，发布命令能立刻结束
nohup java -jar app.jar </dev/null >/dev/null 2>&1 &
```

如果后台进程继承了 stdout，SSH 通道会一直不关闭，构建会**看起来卡住**（实测能挂满子进程生命周期）。

### 2. 健康检查要容错，否则「启动慢」会被判失败

```bash
# 服务刚重启时第一次 curl 一定连接失败（退出码 7）
# 有 set -e 时：连接失败会让脚本立即以 7 退出，重试循环直接失效
if ! status_code=$(curl -s -m 5 -o /dev/null -w "%{http_code}" "${url}"); then
  status_code=000
fi
```

### 3. 不要用管道和 `|| true` 包住要判定的命令

| 写法 | 退出码 | 结果 |
| --- | --- | --- |
| `bash start.sh` | 脚本自己的 | 正确传递 |
| `bash start.sh \| tee log` | `tee` 的 0 | **失败被吞**（需要 `set -o pipefail`） |
| `bash start.sh &` | 0 | **失败被吞** |
| `bash start.sh \|\| true` | 0 | **失败被吞** |

### 4. `set -e` 可以加，但要配套改

- 写在**脚本里**（写在「发布后命令」输入框里对子脚本无效，子进程不继承）；
- 加了之后，任何一步非 0 都会让脚本提前退出——包括上面那种「服务还没起来」的 curl；
- 建议：`set -Ee` + `set -o pipefail`，并把健康检查改成容错写法。

### 5. 日志想实时看就换行输出

```bash
echo -n "..."        # 不换行：服务端按行回调，会攒到最后一次性刷出
printf '.\n'          # 每行刷新，构建日志实时可见
```

## 五、失败之后：产物已经传上去了怎么办

发布顺序是「先上传产物 → 再执行发布后命令」，因此**判失败不会撤回已上传的 jar**。要防「启动失败但线上已经是新包」：

1. 用【SSH 项目】发布：自带版本快照，构建历史里可【快速回滚】切回上一版目录；
2. 或在启动脚本里失败时自行回滚（保留上一版 jar，`exit 1` 前换回去）；
3. 或把健康检查放进「发布前命令」之外的独立步骤，确认服务正常后再切换流量。

## 六、常见问题

### 脚本里 `exit 1`，构建还是成功？
先看日志有没有「执行 发布后命令 类型脚本的退出码是：1」。有这行说明退出码读到了，是「严格执行」没开；没有这行说明版本早于 2.11.15.2。

### 只发了一台就停 / 两台都发了？
停在第一台：`严格执行` + `任一目标失败即终止` 都开着；继续发第二台：其中至少一个没开（见第二节组合表）。

### 日志显示退出码 7，脚本几秒就结束？
典型是脚本里加了 `set -e`，而第一条 `curl` 在服务还没起来时连接失败（7）→ 脚本立即退出，100 次重试失效。按第四节第 2 条改。

### 日志出现「退出码读取不到（-1）」
SSH 通道没有回传退出状态（例如脚本被 `kill -9`、SSH 中断）。2.11.15.2 起：开严格执行按该目标失败处理；未开只提示。

### 只想「脚本失败就停」，不想改构建状态？
不要动「严格执行」——它一定会把该目标判失败。目前没有「只停不判失败」的开关；可用通知/事件脚本自行告警。
